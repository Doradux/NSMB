## Actual C# Translator → generated C++ → Emscripten Wasm test

**A genuine translator pipeline was achieved using only PUBLIC synthetic PowerPC:**

1. `translator-fixture/build_fixture.mjs` writes a **264-byte synthetic DOL** into ignored `translator-fixture/out` with text section at 0x80001000, two 32-bit big-endian instructions `0x38630001` (`addi r3,r3,1`) and `0x4E800020` (`blr`), plus an auto SHA256-pinned manifest. No Nintendo data.
2. Precompiled **upstream Translator.Cli .NET 8** performs `translate-recursive 0x80001000 --project ... --outdir ...`, with its real decoder, lifter, SSA ABI analysis, and `CxxLinearCodeGenerator`. Output `func_80001000.cpp` genuinely contains `extern "C" void func_80001000(CpuContext* MKW_RESTRICT ctx)`, `r3 = (r3 + 1);`, `ctx->gpr[3] = r3;`, and guest ABI metadata `gpr_read/write=0x8`, no FPR/CR/XER effect. This generated file is IGNORE-listed, not checked in as an original game function.
3. `build_translator_fixture.ps1 -Emsdk <authorized SDK> -TranslatorCli <public CLI .dll>` compiles that **actual unedited generated C++ file** with the rest of the existing W03 scheduler, W04 memory, W07 device policy, W08 shared input source and a minimal **test-only** non-hardware shim for its four includes. The shim supplies `CpuContext` and refuses to implement missing memory/HLE helpers. The result is `dist/frame_loop_translated_fixture.mjs/.wasm`, NEVER added to the normal web-server allowlist.
4. The test-only `nsmbw_loop_translated_spawn` schedules one generated C++ function as a bounded host dispatch, preserving per-guest context/state; this symbol is absent from **normal** `frame_loop.wasm`. It is not a general guest PPC stepping engine: the emitted two-op C++ function executes atomically per W03 host tick, with no mid-function suspend/restore.
5. `translator_fixture.test.mjs` verifies r3 + 1, 32-bit wrap, r2/r13, LR/SP/PC, 3 contexts fair order, invalid guest stack and 128 resets. `translator_fixture_browser.test.mjs` uses a localhost four-route HTTP allowlist and REAL Chrome DevTools: three real translator-produced function invocations over 2 requestAnimationFrame callbacks +128 further real browser cycles, verifies no private/test binary escapes, no console exceptions. Both NORMAL and test-only fixture remain strictly separated.

The full .NET **SDK** is not available via `dotnet --list-sdks` on `marcos`, so C# sources themselves were NOT recompiled; the existing upstream-built Translator.Cli binary was executed successfully. The synthetic output is pinned/validated by `build_translator_fixture.ps1`. No new public original image/profile assumptions were made.

## Phase5 follow-up: actual translator-emitted checked scalar memory read

The **second** wholly PUBLIC fixture is `translator-fixture/build_memory_fixture.mjs`:
- Authors another tiny 264-byte public synthetic DOL containing exactly `0x80640000` (`lwz r3,0(r4)`) and `0x4E800020` (`blr`); creates its own pinned SHA256 manifest and dummy non-game SDA; generated binary and C++ are ignored under `translator-fixture/out/memory_fixture/`.
- The REAL precompiled C# `Translator.Cli.dll` emits the unmodified C++ statement `r3 = MemoryInline::FlatRead32(r4);` inside `extern "C" void func_80001000(CpuContext* ...)`. Strict build validation rejects unexpected generator output.
- `build_translator_memory_fixture.ps1` links that EXACT C++ file with W03/W04/W07/W08 into **ONLY** `dist/frame_loop_translated_load_fixture.mjs/.wasm`, compiled with `NSMB_PHASE5_TRANSLATED_LOAD_FIXTURE`. No source/game asset is taken from Nintendo.
- `translator-fixture/include/memory.h` deliberately exposes one **single** checked operation `MemoryInline::FlatRead32(uint32_t guestAddress)`, implemented through `nsmbw_interop_read32` and immediate W07 status/retry metadata. It returns a placeholder zero inside the generated C++ call on failure, but the **frame scheduler invokes the generated function on a temporary CpuContext**, checks W07 status, and only commits its GPR/PC/DONE on success. On failure the original PC/guest registers remain untouched, with fault status 1/4 and no quota/device retry. No guest write, MMIO callback, native pointer, 4 GiB mapping, FPR, resolved range or other helpers are provided.
- The additional test-only export `nsmbw_loop_translated_load_spawn(id,stack,inputGuest,sda2,sda1)` dispatches exactly this known two-op memory-read fixture; absent from normal Wasm and from the previous arithmetic translator fixture. It does NOT implement general translated dynamic function dispatch or arbitrary stackful suspension. The whole generated function remains atomic per W03 host tick.
- `test/translator_memory.test.mjs` checks actual compiled C++ read via cached/uncached W04 aliases, big-endian value 0x12345678, three translated contexts with output isolation, denied MMIO status4, unmapped status1, PC/r3 rollback and 128 resets.
- `test/translator_memory_browser.test.mjs` executes actual Chrome/Brave animation frames: three contexts, invalid device read isolation, 128 genuine RAF resets, and a four-resource localhost allowlist preventing browser exposure of normal fixture, memory DOL, local code and original files.
- This is a **minimal source-independent proof for only `lwz`**. Compiler implementations of `FlatRead8/16/64`, stores, floating-point memory, resolved spans, cross-page writes, device callbacks, code execution protections, privileged instructions, native ABI overrides and generalized fault unwinding are **not implemented**. The technique of a temporary context cannot roll back memory writes, interrupts or device side effects from a more complex generated function, so those unsupported functions MUST FAIL compilation/dispatch rather than being treated as transactional.

The original W01 pinned DOL hash/provenance/audit gate remains unresolved. None of these public synthetic translator checkpoints justify running original game functions or claiming gameplay.
